## Findings and implementation

| Boundary | Finding | Implementation or retained contract |
| --- | --- | --- |
| Prompt → editor | A plain “generate a syllabus” request could inherit a smaller focused section. | Whole-syllabus intent now overrides incidental focus. Exact field requests retain component scoping. |
| Model → patch | Structural failures stopped immediately; a local model returned a JSON Patch envelope instead of editor fields. | Each generation stage allows one bounded repair for JSON, schema, scope, completeness and source failures. Whitelisted whole-field replace envelopes become inert field data; a single outcomes, requirements or policy string becomes a one-item list without changing its wording. Arbitrary paths and operations remain invalid. |
| Whole-syllabus generation | One large completion could omit later weeks or exceed a small model's output budget. | Core outcomes, requirements and policies are followed by batches of four teaching weeks and, when source material exists, a bibliography stage. Batches receive program outcomes and preceding topics. The assembled result passes final validation before one proposal is shown; no intermediate stage applies or saves content. |
| Outline replacement | Completeness checks covered only explicit all-field wording. | Whole-syllabus requests require the seven draft fields and nonempty outcomes, topics, activities, assessments, materials and assessment types for every teaching week. Every outline replacement retains the existing week set and examination labels; whole-syllabus generation copies exam rows unchanged. Explicit outline requests stay within the outline. |
| Institutional rules | A generated policy or grading formula could look like an official rule. | Newly proposed whole-syllabus requirements and policies are labelled for instructor review. Existing grading text is retained; a missing formula is explicitly pending approved institutional guidance. Identity and institutional context are not generated by the whole-syllabus stages. |
| Research → writing | Selected course context could replace a different topic explicitly requested by the user. | Explicit public-search topics take precedence; “this course” resolves against selected-course context. Source-only requests cannot substitute product-guide snippets. No-web instructions disable external research. |
| Prompt → courseware writer | The original prompt was lost after the Generate card, so language and example preferences could not reach inference. | The current request travels through the confirmation card, API and each writer attempt as a bounded 4,000-character field. The writer receives language, level and example instructions while retaining the outline, output schema and draft status. The request text is not added to public search queries. |
| Courseware source scope | A source restriction could disappear between Pulse and week generation or still retrieve unrelated private documents. | No-web restrictions are enforced inside the shared courseware graph even if the API research flag is omitted. No-web alone permits authorized library retrieval. Explicit syllabus/outline-only requests skip library and web retrieval and supply the full bounded syllabus context. Requests tied to uploaded files return actionable `SOURCE_REQUIRED` before searching or generating because this endpoint receives no attachments. |
| Courseware writing | The prompt demanded two tiny lesson sections and fewer than 500 words, and omitted topics after the first twelve. | The writer receives all supported topics and outcomes; instructions request explanations, self-contained examples, practice and useful activity steps. A minimum gate rejects lessons with fewer than 120 words excluding reference sections, or detected placeholder section bodies, and allows one repair. Public research can support an empty or irrelevant library, with retrieved provenance and coverage limitations. |
| Bibliography | Source URL prefix matching admitted adjacent paths or lookalike hosts. | Links require the same origin and an exact path or real descendant path. Returned public references are assembled from retrieved metadata; model-authored reference sections are removed. |
| Provider → browser | Operator calls had a shorter browser wait than local generation; local/browser length stops could appear complete. | Operator waits through the backend budget. Local JSON drafts consume NDJSON tokens as they arrive, avoiding a full-generation wait for response headers; only a completed assembled response enters validation. Malformed/truncated streams, output limits and cancellation fail before application. Successful operator inference updates saved-provider verification; provider errors invalidate it. |
| Roles | The direct courseware service admitted Dean/Associate Dean while HTTP denied them. | Both layers now use the same instructor/admin authoring capability. Student, Dean and Associate Dean access remains unchanged. |
| Patch → persistence | Existing code had real revision-checked saves, but earlier screenshots mostly used synthetic model responses. | Added a provider-transport/API/editor/save/reload regression plus an opt-in real local-model evaluation and real browser capture. A proposal alone never saves. |

## Scanned services and remaining boundaries

Workspace revision checks, local and Supabase ownership, account conversations, file extraction, approved-topic mapping, academic projection, publication timing, assessment sessions/marking and in-app notices are implemented services, not placeholder success messages. Their existing role/RLS and browser suites remain release checks. No permissions were widened.

The named guide agents are authored workflow guidance; the LangGraph agents are bounded processing stages. They are not separate autonomous employees. Model output cannot execute arbitrary code or invent application tools. The current harness supports navigation, guidance, syllabus/roster edits, courseware drafting, private recall and external research within those existing controls.

The 120-word gate establishes minimum content, not factual correctness or teaching quality. Outline coverage and answer-key agreement are review aids, not independent proof that a lesson is accurate. Generated policies remain proposals, and bibliography entries require supplied metadata. A failed stage or exhausted repair returns an error without a partial syllabus save; resource-constrained local models can still fail to complete a valid request.

The source-only week-generation boundary is deliberately narrower than Pulse's file-reading workflow. It can use the selected syllabus supplied with the request; it cannot claim access to a chat attachment that was never delivered to the courseware API. The Generate card displays the server's error message and retains its existing **Draft in chat instead** action. The API does not silently substitute the knowledge library for a requested upload.

Direct EduSuite synchronization, email/push notifications, automatic vector indexing of every lifecycle upload, and calendar-driven late-routing alerts remain separate unimplemented services in the preservation register. This content-harness pass does not claim those delivered, and it does not remove their UI contract. Offline institutional approval remains intentionally human. Hosted provider capability and inference quality still depend on the connected account/model.

**Content review finding:** the courseware trial above still contains factual errors: it incorrectly presents `:=` as JavaScript assignment and calls a `let` binding a constant. ## Reproduction scope

The live API evaluations use `npm run eval:harness` with `AI_PROVIDER=ollama`, a dedicated `AI_DATA_DIR` containing `harness`, and an already installed model. `HARNESS_WHOLE=true` exercises all syllabus weeks; `HARNESS_COURSEWARE=true` adds real courseware generation and persistence. The temporary service used `OLLAMA_BASE_URL=http://127.0.0.1:11439`, `OLLAMA_MODEL=qwen2.5:3b`, `AI_ONNX_THREADS=1` and `AI_TIMEOUT_MS=600000`. No model output was substituted. The browser capture ran `npx playwright test --config playwright.snapshots.config.ts harness-delivery.spec.ts` after `npm run build:capture`, with `SNAPSHOT_MODEL=qwen2.5:3b`, isolated ports/database and `AI_TIMEOUT_MS=540000`.

The desktop/mobile regression suite uses its existing synthetic auth fixtures and a nonsecret dummy publishable key. It checks role UI and local persistence; hosted Supabase authorization, provider billing and production deployment are not established by those fixtures. The isolated checkout preserves the baseline landing implementation because another active task owns landing changes in the shared workspace.
